RAGNAROK AGENTS - USER GUIDE
===========================
Updated: 2026-10-29 (America/Santiago)

WHAT WE ARE BUILDING
--------------------
Believable AI players on a classic/pre-Renewal Ragnarok Online private
server. First prove one persistent, grounded player. Then build a small
community whose first shared experience is cooperative PvE and simple
trade. Expand to five players only if quality and resources allow it.

WHERE WE ARE
------------
  [DONE] M0 - Environment and deployment choice.
         Native Windows setup selected and documented.

  [DONE] M1 - Server/client bridge.
         rAthena, OpenKore and Python passed a 600-second connection
         trial with movement, chat and reconnect. A later framing fix
         passed a targeted test and a five-second live run; it has not
         had a second 600-second run. No autonomous AI player exists yet.

  [NEXT] M2 - Local inference benchmark.
         Compare two local model candidates, measure performance and
         bring sample conversations to you for quality review.

  [WAIT] M3 - One persistent agent, after M2 is accepted.
         Identity, grounded dialogue, routine gameplay, memory across
         restart and reliable fallback behavior.

  [WAIT] M4 - Three-agent community, after M3 is accepted.
         Distinct identities, cooperative PvE, simple trade and a
         one-hour trial with human review.

  [OPTIONAL] M5 - Five-agent scale check, after M4 passes.

These labels reflect evidence, not just completed code. The detailed
acceptance criteria are in docs/ROADMAP.md. Actual handoff facts are in
docs/CURRENT_STATE.md; M0 and M1 evidence is under docs/evidence/.

HOW TO USE THE CHATS
--------------------
- Keep this existing planning/review chat as the main coordinator. Use
  it to assess evidence, decide whether a milestone passes and update
  the plan. It integrates accepted work into GitHub main.
- Use one focused implementation chat per milestone. Continue fixes in
  that chat; do not make a separate chat for every file or test.
- The implementation chat should inspect Git status and relevant docs,
  work on a codex/ branch, commit small verified steps with descriptive
  messages and push regularly. One prompt does not require one commit.
- Avoid two chats writing to the same checkout at the same time. Use
  separate worktrees only if parallel work becomes useful; shared game
  services, database, ports and GPU still need coordination.
- At handoff, ask for: branch/commit range, changed behavior, checks
  actually run, evidence paths, limits and one proposed next action.
  Bring social-quality samples back here for your own review.
- Keep credentials, raw logs, model weights and databases out of Git.
  Update this guide when milestone status or direction changes; use
  docs/CURRENT_STATE.md for more detailed handoffs.
